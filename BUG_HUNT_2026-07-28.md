# Bug Hunt — 2026-07-28

Multi-agent hunt for **real** correctness/security bugs (not style/dead-code).
Method: 4 region-scoped hunter agents (OT protocols, IoT/health/discovery, fuzz,
pcap listeners) + manual sweep of top-level/utils/targets. Every finding below was
verified against the pinned library versions or the module's own contracts.

Bug classes hunted: (1) exception-swallowing that flips a security verdict,
(2) wrong tshark/lib field/attr names → silent-empty extraction, (3) error-vs-
negative conflation, (4) credential/parse-robustness, (5) logic bugs.

## Open — verified, not yet fixed (ranked by severity)

### CRITICAL (snap7 — verified against pinned python-snap7 3.0.0, a pure-Python fork)
- `snap7/mixins/security.py:224` — **brute-force reports a false "weak password" on every readable S7 CPU.** Pinned `Client.set_session_password` is a **no-op stub** (`self.session_password = password; return 0`, never contacts the PLC), and the loop's oracle `get_cpu_state()` is an *unauthenticated* diagnostic that succeeds regardless of protection. So the first wordlist password "succeeds" → `report_credential` + "Weak password" AUTHENTICATION finding for a password the PLC never checked. **Fix needs a real S7 target and a genuinely auth-gated oracle (or the feature must be disabled/caveated) — the pinned lib cannot authenticate at all.**
- `snap7/mixins/security.py:280` — **null-password check reports "Empty password accepted / No authentication" on every readable PLC** (same stub `set_session_password("")` + unauthenticated `get_cpu_state()`). Same fix constraint.

### HIGH
- `snap7/szl_parser.py:191` — protection-level probe reads wrong offsets → **password-protected PLC reported UNPROTECTED**. Fix: parse from `szl.Data[:LengthDR]`, skip record-index word, `struct.unpack(">H")` per protection word.
- `snap7/szl_parser.py:55` — python-snap7 3.0 `read_szl()` returns an `S7SZL` ctypes struct (Header{LengthDR u16, NDR u16} + Data[16380]); callers pass `bytes(szl)` so records are 4 bytes misaligned and read little-endian instead of big-endian → all SZL module/device-ID extraction garbage. Fix: callers pass `bytes(szl.Data[:szl.Header.LengthDR])`; parse header words big-endian.
- ~~`iec104/constants.py:46` — COT-is-2-octets offset fix~~ **FIXED (7455343).**
- `snap7/mixins/slot_scan.py:130,143`, `device_info.py:163`, `block_operations.py:415` — `SZLParser.parse(..., bytes(szl))` passes the whole 16 KB `S7SZL` ctypes struct instead of the payload. `read_szl()` puts the payload in `.Data` with `Header.LengthDR=len`, so `bytes(szl)` prepends the 4-byte `{LengthDR,NDR}` header → records shifted 4 bytes and `record_len` read from the native-LE header word → order_code/module_type extraction garbage. Fix: `bytes(szl.Data[:szl.Header.LengthDR])` (the pinned lib's own `read_szl_list` does exactly this).
- `snap7/szl_parser.py:138,139` — `_parse_0x0011` reads `record_len`/`partial_list_len` little-endian; SZL LENGTHDR/NDR are big-endian on the wire (a distinct instance of the known :55 BE bug, in a different parser) → order_code/serial records mis-walked. Fix: `"big"`.
- `snap7/mixins/block_operations.py:352` — `list_szl_ids` reads directory SZL-IDs little-endian and from offset 0 → 0x0011 reported as 0x1100 and the 4-byte header treated as bogus IDs. Fix: `"big"` and skip the 4-byte header.
- `snap7/mixins/security.py:315` — `_analyze_security` defaults `protection_level=3` (most-secure) when `_check_protection_level()` returned None (probe raised) → `authorization=True`, `access_control=True`, no finding; a crashed probe masks a wide-open PLC. Fix: treat None as indeterminate. (MED)
- `snap7/mixins/memory.py:236,256` — `tm_read`/`ct_read` `count` is a BYTE size in the pinned lib, but timers/counters are 2 bytes each → passing a count reads count/2 items. Fix: pass `count*2`. (LOW)
- `mms/cli_runner.py:265` (+ `mms/__init__.py:126`, `mms/protocols` write/read paths) — fuzzer crash counter effectively unreachable: nested `except Exception: return None/False/b"\x00…"` in `write_value`/`_write_under_fc`/`read_value` swallow a connection reset, so a real target crash is recorded as a benign "failed write" and the run prints "0 crashes".
